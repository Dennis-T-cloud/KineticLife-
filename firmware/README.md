# KineticLife Firmware

ESP32-S3 firmware workspace for camera bring-up, WiFi pairing (QR + Soft AP), WebSocket binary streaming, and LED behavior.

## Hardware Baseline

- Board: Freenove ESP32-S3-WROOM Board (N16R8), FNK0085 B
- Camera: OV2640 140° wide-angle
- Memory target: 16 MB Flash / 8 MB PSRAM

## Quick Start

```bash
pio run
pio run --target upload
pio device monitor
```

## WiFi Pairing

The firmware stores WiFi credentials in NVS only as the active demo session. There is no default hotspot fallback. Boot behavior:

- NVS has an active session → connect to WiFi, start HTTP server + WebSocket.
- NVS is empty → enter Pairing Mode (blue LED flashing), offer **two paths** simultaneously:

### Path 1 — Soft AP (Config Tab in pair.html)

1. ESP32 broadcasts a soft AP: **SSID `KineticLife-Setup` / password `kineticlife`**
2. Laptop connects to `KineticLife-Setup` (leave phone hotspot temporarily)
3. Open `web/pair.html` → Config tab → pick target WiFi → enter password → Connect
4. ESP32 connects, saves credentials, reboots
5. Laptop reconnects to phone hotspot; find device via mDNS `fitcam-xxxxxx.local`

### Path 2 — QR Camera Scan

1. Keep laptop on phone hotspot
2. Open `web/pair.html` → generate QR for the hotspot (SSID + password)
3. Hold QR ~30 cm from ESP32 camera (phone screen at 100% brightness, **screen must stay on**)
4. Firmware parses QR, connects, saves, reboots

> **iOS hotspot note**: iOS hides the hotspot SSID when the screen is off.  
> For QR path: keep phone screen on during the entire scan.  
> For Soft AP path: this does not apply — ESP32 connects via `WiFi.begin()` directly.

QR format accepted:

```text
K1:W:<SSID_LEN>:<SSID><PASSWORD>   (compact, generated by pair.html)
WIFI:S:<SSID>;T:WPA;P:<PASSWORD>;;  (standard, any QR generator)
```

To end a session (clears NVS and reboots to pairing):

```text
POST http://<ESP32-IP>/end
```

To force pairing without a serial connection:

```bash
pio run --target erase
pio run --target upload
```

The external HTTP and pairing contracts are defined in `../docs/04_Interface_Contracts.md`.

## Camera Configuration

Current streaming mode (`camera_init()`):

| Parameter | Value | Notes |
| --------- | ----- | ----- |
| Resolution | FRAMESIZE_QVGA (320×240) | QVGA uses a wider sensor crop → larger FOV at 1m |
| JPEG quality | 12 | Configured at init and reapplied by debug/demo pages via `/cam?res=320x240&q=12` |
| Frame buffers | 2 in PSRAM | fb_count=2 eliminates DMA bus contention with WiFi |
| XCLK | 20 MHz | Hard limit on FNK0085B — 24 MHz causes screen tearing |
| Target fps | ~15 (67ms/frame) | `FRAME_MS=67` in `http_server.cpp` |

Observed target: OV2640 captures around 9fps at 320×240 JPEG on the current WebSocket pipeline. FRAME_MS just throttles the send rate; actual fps is camera-bound.

QR pairing mode (`camera_init_qr()`): GRAYSCALE QVGA, 1 buffer in DRAM.

## Streaming Architecture

Firmware uses **ESPAsyncWebServer + AsyncWebSocket** (non-blocking). Transport:

- Endpoint: `ws://<IP>/ws`
- Format: binary frames, each frame is one complete JPEG
- Latest-frame policy: firmware sends only to clients whose WebSocket queue is empty
- Slow clients skip stale frames instead of accumulating old JPEGs
- `esp_camera_fb_return(fb)` — called right after per-client send attempts, safe because accepted frames are already copied
- `ws.cleanupClients()` — called every loop tick to reclaim closed-connection memory

REST endpoints: `GET /hello`, `GET /status`, `GET /capture`, `GET|POST /cam`, `GET|POST /end`

## Optional BLE Throughput Test

ESP32-S3 supports BLE, not Bluetooth Classic. The BLE code is isolated behind a separate PlatformIO environment so the normal WiFi/AP camera firmware stays unchanged at runtime. The BLE test firmware waits briefly for OV2640 power stabilization, initializes the camera in low-resolution snapshot mode, verifies one captured frame, then advertises the GATT service. It intentionally skips WiFi/AP, HTTP, and WebSocket startup.

```bash
pio run
pio run -e freenove_esp32s3_wroom_n16r8_ble_test --target upload
pio device monitor
```

When flashed with the BLE test environment, the device advertises as:

```text
KineticLife-BLE-<mac6>
```

GATT contract:

| Item | UUID | Direction |
| ---- | ---- | --------- |
| Service | `9b8f0001-6f4d-4d4f-9c9a-4b4c49464501` | discover |
| TX notify | `9b8f0002-6f4d-4d4f-9c9a-4b4c49464501` | ESP32 -> phone |
| RX control | `9b8f0003-6f4d-4d4f-9c9a-4b4c49464501` | phone -> ESP32 |

Control commands written as UTF-8 text:

```text
size=<8..180>
gap=<4..100>
start=<1000..60000>
cam=<1000..60000>
stop
```

`start` sends synthetic notification payloads. `cam` initializes the OV2640 at 160x120 JPEG quality 30, then sends repeated JPEG snapshots as `CAM:<frame_id>:<bytes>:<chunks>:<size>:<q>` metadata followed by raw JPEG chunks. Open `web/pair.html` -> **BLE Test** to run the browser-side counter and camera snapshot preview, or open `web/demo-table.html?source=ble` for the experimental BLE -> JPEG decode -> MediaPipe -> exercise-feedback path. Web Bluetooth generally works on Android Chrome from a secure context (HTTPS or localhost). iOS Safari does not expose Web Bluetooth; use a native BLE app such as nRF Connect for phone-side smoke tests.

## Performance Log Guide

Useful serial log lines:

```text
[boot] KineticLife firmware=0.3.0
[perf] camera_init_ms=... mode=stream format=JPEG frame=320x240 q=... heap_kb=... psram_kb=...
[perf] wifi_connect_ms=... ip=... rssi=... attempts=...
[perf] http_start_ms=... setup_total_ms=...
[ws] connect id=... ip=... clients=... heap_kb=... psram_kb=...
[ws] perf elapsed_ms=... sent=... dropped=... fps=... cap_avg_ms=... cap_max_ms=... jpeg_avg=... clients=... backpressure_skips=... rssi=... heap_kb=...
[status] state=... uptime=...s ip=... rssi=...dBm heap_kb=... streams=...
```

How to read them:

- `cap_avg_ms` near 100ms at 320×240 JPEG: normal for the current OV2640/140° calibration target (~9fps).
- `dropped=0`: no whole-frame drops. Nonzero `backpressure_skips` means slow clients skipped stale frames to preserve realtime display.
- `heap_kb` stable 164–184KB: healthy. Sudden large drop = memory leak.
- `psram_kb` stable ~8144KB: normal. Dip below 7000KB = PSRAM pressure.
- `rssi` better than `-65dBm` required for stable streaming.

## Web Debug Page (`web/debug.html`)

Connects to the ESP32 via WebSocket (`ws://<IP>/ws`). Frame pipeline:

1. `onmessage` receives binary JPEG → `createImageBitmap()` decode (off main thread)
2. Backpressure: `decodePending` flag + `pendingData` slot — at most 1 pending decode, newest frame wins
3. Decoded `ImageBitmap` drawn to 240×320 canvas with 90° CW rotation (landscape camera → portrait display)
4. MediaPipe PoseLandmarker (VIDEO mode) on 120×160 offscreen canvas → 14 joint angles
5. Sliding window: 60-frame circular buffer (visibility-filtered: skip if < 8 valid joints)
6. DTW comparison runs in a Web Worker (non-blocking) every 15 frames against a loaded reference

Status bar shows: `fps  detect_ms  avg:Xms  vis:N/14  match:%`

Normal values at ~9fps hardware rate: `detect avg 20–40ms`, `fps ≈ 9`.

ESP32 camera must be physically rotated 90° CW to match the portrait canvas.
